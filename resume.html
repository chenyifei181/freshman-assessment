🐾 先说说我是个什么样的人

我叫陈一菲，来自广东湛江，现在在广东工业大学读集成电路设计与集成系统创新班，大一。 如果只能用一个特点介绍自己，我想说：我是一个对"发现问题"上瘾的人。

别人做实验做到"能跑通"就收工了，我总忍不住再回头多看两遍。不是不放心，而是真的觉得—— 在所有人以为"这没问题"的地方找出一处漏洞、一个藏得很深的 bug，是一件特别让人兴奋的事。 也正因为这个性格，我对数字 IC 里的芯片验证格外感兴趣：验证的本质，就是在设计被大家认为"应该没问题"的时候， 尽量把那些意外情况提前找出来。这和我这个人太合拍了。

🐾 为什么想往芯片验证走

我享受的不是"造出东西"的那一下，而是"把可能出错的地方一个个试出来"的过程。

我读的本来就是集成电路设计与集成系统，走数字 IC 这条路对我来说是顺理成章的； 而在这条路上，最吸引我的就是验证。 这次考核里我做小游戏的时候，最花时间的不是写功能，而是想办法让 AI 不会把自己困死： 我先想清楚"它在什么情况下会死"，再一条条加上检查（能不能回到尾巴、剩余空间够不够）。 那种"我提前想到了别人没想到的情况"的感觉，和我想做验证的冲动是同一件事。 我还没系统学过验证的课程，但我有耐心、愿意钻，也清楚自己想往哪个方向走。

🐾 我是怎么做这些作品的

  • 用 Git 管理版本，全部作品提交在自己的 GitHub 仓库里，能看出是一步步改出来的
  • 用 AI 编程工具生成初版，但每一段关键逻辑我都自己核对过、改过（提示词和迭代过程都记在 README 里）
  • 电路部分坚持先手算一遍公式，再拿仿真结果对照，对不上就回头找原因
  • 举个能说明我这人习惯的例子：AI 曾经很确定地告诉我，git checkout -- . 可以"安全地撤销改动"。 我去查了 Git 官方文档，又在一个测试文件夹里亲手试了一次——结果是它会直接把未提交的修改丢掉，而且找不回来。 这条「AI 说错了、我自己查证纠正」的完整过程我写进了 README。对我来说，查证的过程比结论更重要。
  • 还有一次是真的失败，但最后做成了：上传作品的时候，GitHub Desktop 反复弹出 Failed to push，报错写着 Recv failure: Connection was reset，连着试了三次都没成功。 我没有一直硬点，而是先把这句报错查清楚是什么意思（大概是上传过程中网络连接被中断了）， 然后换了一个网络重新上传，就成功了。这件事让我记住两点：遇到报错先看懂它，再动手； 失败的时候换个条件再试，比原地重复有用。
